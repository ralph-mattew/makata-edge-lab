WHAT A POC IS (calibrate on this — it is the most common mis-grade):
A PoC is a PRE-REGISTERED TRANSFER experiment. The source almost never ran on our exact
stack (CUAD contracts + EmbeddingGemma 300M + Qwen2.5-1.5B Q4, 6GB iPhone, hybrid
0.9/0.1, recall@3). So the source NOT having measured our dataset/model/metric is EXPECTED
and is NOT, by itself, a reason to fail. The PoC exists precisely to test that unverified
transfer. Judge the MECHANISM's clarity and reimplementability, not whether the source
pre-confirms our numbers.

TWO DISTINCT FAILURE MODES — only these should drive a FAIL:
  (A) MECHANISM ABSENT: the source does not actually describe HOW the method works
      concretely enough to reimplement (black box, hand-wave, or the idea's described
      mechanism is not in the source at all). Classic example: PoC 011 assumed naive
      text-prepending would match Anthropic's fine-tuned contextual embeddings — the
      source never described that mechanism. FAIL.
  (B) SOURCE MISREPRESENTATION: the idea claims the SOURCE PROVES an outcome it never
      measured, or attaches our dataset/metric to the source as if the source reported
      it. FAIL — but ONLY if the idea misrepresents. If the idea HONESTLY separates
      `source_establishes` from `transfer_hypothesis` and discloses the gap in
      `source_limits`, that honesty is a STRENGTH, not a red flag.

Do NOT fail an idea just because: the source used a different corpus/model/metric; the
predicted number isn't in the source; or the mobile port is non-trivial but plausible.
Those are the normal conditions of a transfer PoC. Reserve low scores for (A) and (B).

If a web_search tool is available, USE IT to check whether a real, usable implementation
exists (open-source repo; llama.cpp / MLX / Core ML support for on-device use). Cite what
you find in `evidence`; if no on-device-viable implementation exists, note it in
`red_flags` and score `implementation` lower — but a reimplementable mechanism described
in the source can still score well even without a packaged mobile library.

GATE 2 CRITERIA (score each 0-10):

1. **Core mechanism explained** — does the SOURCE describe HOW it works concretely enough
   to reimplement? 0: black box / not in source; 10: concrete, reproducible mechanism.

2. **Implementation path identified** — is there a plausible path (named libraries/models/
   hyperparameters, or a clear reimplementation from the source) to run it on our stack?
   0: no path / asserted but unsupported; 10: concrete and mobile-viable.

3. **Transfer hypothesis well-posed** — is the leap from the source's setting to ours
   stated EXPLICITLY, with a falsifiable prediction and an unambiguous decision rule?
   0: no prediction, or the idea pretends the source already proves our outcome; 10: the
   transfer is named, the prediction is falsifiable, and the decision rule is crisp.
   (Reward honest `transfer_hypothesis` + `source_limits`; penalize misrepresentation.)

4. **Failure modes understood** — does the idea honestly state when this will NOT work on
   our stack (the disclosed `source_limits` and on-device risks)? 0: no awareness / hides
   the gap; 10: clear, specific failure-mode analysis.
