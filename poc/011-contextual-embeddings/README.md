## Question

Does **Anthropic-style contextual retrieval** — prepending a *model-generated* per-chunk
context (not a static template) to each chunk before embedding and BM25 — improve recall@3
on CUAD contracts over the current hybrid baseline, and can a **1.5B model small enough to
run on-device** generate context good enough to capture the gain?

## Why it matters here

[PoC 007](../007-embedding-retrieval-recall) found the median chunk is 25 words. Small
chunks lose context: "30 days" could be a notice period, payment term, or warranty; "State
of Delaware" could be governing law, venue, or domicile; "as described in Section 3.2" is
meaningless alone.

Anthropic's **Contextual Retrieval** addresses this by having a language model *write* a
short context for each chunk, situating it in its document, then prepending that generated
context before embedding and BM25 indexing. They reported top-20 retrieval-failure rate
dropping ~35% (contextual embeddings + contextual BM25), or ~49% with a reranking stage.

**The mechanism is generation, not a template.** The original 011 draft (see Deviations)
tested a *static* prepend — document title + a heuristically-extracted section header. That
is a strawman: it is not Anthropic's method, and PoC 011 was flagged internally for exactly
this mechanism mismatch. This revision tests the real method and keeps the static prepend
only as an **ablation**, so the experiment can show whether the generation step — not merely
adding any surrounding text — is what matters.

**The open question for this lab is on-device feasibility of the generator.** Anthropic used
a large model (Claude) to generate contexts. Xylo's on-device budget affords only
Qwen2.5-1.5B Q4. Two things are therefore unknown and worth measuring:
1. Does the method transfer to CUAD at all (does generated context beat the baseline)?
2. Is a 1.5B on-device model a good enough context generator, or does the gain depend on a
   large model?

The cost is a **one-time, offline indexing cost** (one short generation per chunk), not a
per-query cost. Anthropic make it cheap with prompt caching of the document prefix; the same
lever applies here (cache the whole-document prefix across all of a document's chunks).

## Hypotheses

All HYPOTHESIS until measured. A point is a percentage point of items. Baseline is the
hybrid retrieval recall@3 of 61.4% (EmbeddingGemma, PoC 007), at the 0.9/0.1 semantic/BM25
weight adopted in [PoC 013](../013-weight-tuning).

1. **H1 (method transfers, strong generator).** Generated contextual retrieval (contextual
   embeddings + contextual BM25), using a strong *host* generator, improves recall@3 by
   **≥5 points** over baseline.

2. **H2 (small on-device generator is good enough).** Context generated by on-device
   Qwen2.5-1.5B Q4 captures **≥60%** of the host generator's recall gain (i.e. most of the
   benefit survives a tiny generator).

3. **H3 (generation beats a static template).** The static prepend ablation (doc title +
   heuristic section, the original draft's method) yields **<½** the recall gain of generated
   context — confirming the generation step, not merely added text, is what matters.

4. **H4 (small-chunk benefit).** The gain concentrates in small chunks (<25 words, Q1);
   chunks >36 words (Q4) gain little.

5. **H5 (indexing cost, on-device).** With document-prefix prompt caching, per-chunk context
   generation with Qwen2.5-1.5B adds an acceptable *one-time* indexing cost: median
   **≤2 s/chunk** on the host stage, and the contextual index grows **≤2×** vs the plain
   index. (Device-stage timing and thermal are a follow-up; see Limits.)

Descriptive: per-category recall, retrieval precision, and qualitative analysis of which
chunks benefit (cross-references, ambiguous terms, entities).

## Method

**Host.** MacBook Pro (Mac16,8), Apple M4 Pro, 24 GB, macOS 26.5.1, on AC power (as PoC 009).

**Embedding model.** EmbeddingGemma-300M (as PoC 007; llama.cpp, Metal).

**Generator models (context writer).** Two, to separate "does the method work" from "does a
small model suffice":
- **Host generator** (upper bound): a strong instruction model run on the host.
- **On-device generator** (realistic): Qwen2.5-1.5B-Instruct Q4_K_M, the same file as PoCs 003–009.

**Context generation prompt** (Anthropic's, verbatim intent):

```
<document>
{WHOLE_DOCUMENT}
</document>
Here is the chunk we want to situate within the whole document:
<chunk>
{CHUNK_TEXT}
</chunk>
Give a short, succinct context to situate this chunk within the overall document for the
purposes of improving search retrieval of the chunk. Answer only with the succinct context
and nothing else.
```

The generated context (target ≤100 tokens) is prepended to the chunk for **both** the
semantic embedding and the BM25 term index (contextual embeddings **and** contextual BM25).
The whole-document prefix is prompt-cached across all chunks of a document to bound cost.

**Model (for key-fact measurement).** Qwen2.5-1.5B-Instruct Q4_K_M (as PoCs 003–009).

**Tooling.** llama.swift 2.8901.0, Swift 6.3.3. Reuse PoC 006's `GGUFQA` harness and PoC 007's
retrieval code.

**Items.** PoC 007's 1,325 answerable items from 397 CUAD v1 contracts (CC BY 4.0).

**Conditions.** Same 1,325 items; hybrid retrieval at 0.9/0.1 (PoC 013), top-3.

| Condition | What is embedded + BM25-indexed | Context source |
|---|---|---|
| `standard` (baseline) | plain chunk text | — |
| `naive-prepend` (ablation) | `"Document: {title}. Section: {header}. Chunk: {text}"` | static template + heuristic section extraction |
| `generated-host` (upper bound) | generated context + chunk | host generator |
| `generated-device` (primary) | generated context + chunk | on-device Qwen2.5-1.5B Q4 |
| `generated-device + rerank` (exploratory) | as above, then cross-encoder rerank top-3 of top-20 | on-device generator; rerank ties to [PoC 012](../012-cross-encoder-reranking-DRAFT.md) |

Both the embedding and the BM25 scores are rebuilt per condition from the (possibly
contextualized) chunk text. Queries remain plain (see Limits #6).

**Measurements.**

1. **Recall** (primary): share of items where top-3 chunks cover ≥50% of CUAD's answer span
   (PoC 007's definition).
2. **Key fact right**: on the 464 items with parsable key facts, whether Qwen's answer
   contains the fact (PoC 006's scorer).
3. **Per-chunk-size recall**: recall by chunk-word quartile (Q1 <18, Q2 18–25, Q3 25–36,
   Q4 >36) to test H4.
4. **Context-generation cost**: per-chunk generation time (median, p90) and token counts,
   for both generators, with and without document-prefix prompt caching; total index size
   per condition.
5. **Retrieval precision** (exploratory): of top-3, how many cover any part of the answer.
6. **Descriptive**: per-category recall and key-fact rates, generated-context length
   distribution, examples of generated contexts.

**Intervals.** 95% CIs via contract-level bootstrap (10,000 resamples, seed 0), as PoC 009.

## Decision rule

Written before the first run. The idea under test: generated contextual retrieval (contextual
embeddings + contextual BM25).

**Step 1 — does the method transfer (host generator)?** Compare `generated-host` vs `standard`.
- H1 holds (recall +≥5 points): proceed.
- recall +2 to +4.9: **inconclusive** — real but modest; weigh against cost (step 3).
- recall <+2 or worse: **reject (host stage)** — contextual retrieval doesn't transfer to CUAD.

**Step 2 — is a small on-device generator enough?** Compare `generated-device` vs `generated-host` (H2).
- `generated-device` captures ≥60% of the host gain: **on-device viable**.
- <60%: the method works but **depends on a large generator** — reject for the on-device target (record as a host-only positive).

**Step 3 — cost (H5).** One-time indexing cost with prompt caching acceptable (≤2 s/chunk median host; index ≤2×)?
- yes → **adopt (host stage)** if steps 1–2 passed; recommend contextual retrieval with the on-device generator.
- no → **adopt (conditional)**: method works but indexing cost needs engineering before device use.

**Ablation (not a gate).** H3: if `naive-prepend` reaches ≥½ the `generated-*` gain, the
generation step matters less than assumed; if it's near baseline, it confirms the original
draft would have failed for the right reason.

**Reranking arm** is reported separately to inform PoC 012; it does not gate this verdict.

## Deviations

- **2026-10-20 (before first run):** Rewrote the registration to test the actual Anthropic
  Contextual Retrieval mechanism — a *model-generated* per-chunk context prepended before
  both embedding and BM25 — instead of the original draft's *static* template prepend
  (document title + heuristically-extracted section header). The static prepend is retained
  only as the `naive-prepend` ablation. Added the on-device-generator question (H2),
  contextual BM25, document-prefix prompt caching for cost, the 0.9/0.1 hybrid weight from
  PoC 013, and an exploratory reranking arm. No run had occurred at the time of this change.

## Limits

1. **Generator quality is itself under test.** A 1.5B model may write weak or wrong contexts;
   that is the point of H2, not a confound to hide.
2. **Answerable items only** — absent-clause behaviour (PoC 008) is not measured here.
3. **CUAD contracts only** — may not generalize to other document types.
4. **Top-3 only** — does not re-test the optimal chunk count (PoC 009) under contextual retrieval.
5. **EmbeddingGemma only** — other embedders may react differently to generated context.
6. **Query not contextualized** — queries stay plain (users don't know the document at query time for cross-document search).
7. **English only** — Xylo's Filipino use case is not tested.
8. **Device stage deferred** — host measures feasibility; iPhone generation time, memory, and thermal are a follow-up.
9. **Single seed** for Qwen runs (seed=1, PoC 009); seed variance (~±2 points) not explored.
10. **Reranking** is exploratory here; a full cross-encoder study is PoC 012.

## Reproduce

Requirements: Apple-silicon Mac (macOS 26.4+, Xcode 26, Swift 6.3+), ~4 GB free memory.
Prerequisites: PoC 006, 007 folders (harness, chunk index, embedding model).

```bash
cd poc/011-contextual-embeddings
./generate-contexts.sh   # LLM-generate per-chunk context (host + device generators), prompt-cached per document
./embed.sh               # re-embed + rebuild BM25 for each condition
./run.sh                 # retrieval + Qwen Q&A for all conditions
python3 compare.py       # recall, key-fact, per-chunk-size, generation-cost comparison
```

Expected runtime: context generation dominates (one short LLM call per chunk; prompt caching
keeps it tractable). Reuse PoC 007's standard embeddings for the `standard` condition.
